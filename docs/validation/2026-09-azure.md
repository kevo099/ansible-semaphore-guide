# Validation record: Azure, September 2026

[Back to validation and limits](../VALIDATION.md) · [Azure chapter](../13-azure.md)

On 28 September 2026 the Azure chapter and its example files were run end to
end in a disposable resource group, which was then deleted.

## How it ran

- **Subscription and region:** a sponsored subscription in `eastus2`, reached
  with an Azure CLI login that held the Contributor role.
- **Tooling:** the Azure playbooks ran from a workstation, in a separate
  virtual environment with ansible-core 2.21.4, `azure.azcollection` 4.0.0 and
  the collection's own requirement set (169 packages).
- **Controller:** Ubuntu 24.04 (`Standard_D2als_v6`), created by `controller.yml`
  and installed with the guide's Ubuntu installer at tag `v1.3.0`.
- **Targets:** Ubuntu 24.04 and AlmaLinux 9.8, created by `targets.yml` with
  cloud-init; and RHEL 9.8 (pay-as-you-go image), created with a plain
  `az vm create` and no custom data, to stand in for a VM that already exists.
  All three were `Standard_D2als_v6` with private addresses only, in the
  controller's VNet.
- **Secrets:** the sudo passwords were generated for the run and delivered on
  standard input; none appears in a command line or in the records.

## Found and fixed during the run

- On `localhost`, Ansible discovered the system Python instead of the virtual
  environment and could not import the Azure SDK. Each playbook now pins
  `ansible_python_interpreter` to `ansible_playbook_python`.
- The bootstrap playbook first read the controller's address from gathered
  facts, which under `become` hold root's environment; it now reads
  `SSH_CONNECTION` in a task without `become`.
- Public CI could not syntax-check or lint the Azure examples without the
  collection. It now installs the pinned collection, without the SDK, first.

## Review and retest

An adversarial review of the branch against these logs and the collection's
source found fourteen problems. All were fixed, and the changed paths were
tested again on a second, smaller lab (a controller, an Ubuntu cloud-init
target and a RHEL VM created with the Azure CLI) that was then deleted.

| Finding | Fix | Retest result |
| --- | --- | --- |
| Azure's default `AllowVNetInBound` opened every controller port to the VNet | `controller.yml` adds a deny-all rule at priority 4000 | Azure's effective rules list the deny ahead of the default; a target could not reach the controller's SSH port |
| `remove_on_absent: all` could follow a VM's attachments into other resource groups | `remove.yml` checks each VM's `owner` and `purpose` tags, deletes the VM alone, and removes the lab's NICs and public address by name | A wrong owner tag was refused with nothing removed; the lab's objects were removed and nothing else |
| `remove.yml` failed on a lab that was already gone | It stops cleanly when the resource group is absent and lists VMs once instead of reading each by name | A rerun after a partial removal finished the job; a run on a deleted lab ended with `changed=0` |
| SSH was reloaded before the effective policy was checked | The drop-in is written with a backup and checked with `sshd -t` and `sshd -T` before a handler reloads SSH | With an earlier `Match` block forcing password login: the run failed, the hand-edited drop-in was restored byte for byte, no reload happened, and key login still worked. On a fresh target the created drop-in was removed |
| A later `NOPASSWD` rule would pass the sudo check | `sudo -k -n` as `svc_ansible` must fail | A planted override made the run fail; after removing it the run passed |
| One key only, which could replace the seeded controller's Semaphore key | `automation_public_key_files` takes a list | Two keys were authorized and both logged in; a repeat reported `changed=0` |
| A key comment containing `: ` broke the cloud-init YAML | The templates quote the key with `to_json` | cloud-init installed a key whose comment contains `: ` |
| The chapter's `python3 -m venv`, working directories and some claims | `python3.12`, explicit locations, narrower wording | Documentation only |

After the power cycle in the retest, the target kept its private address and
answered Ping.

## Not established

- Other regions, VM sizes, Trusted Launch VMs and Rocky Linux on Azure.
- Targets reached across a site-to-site VPN rather than inside one VNet.
- A controller-side managed identity; provisioning used a workstation CLI login.
- `azure.azcollection` versions other than 4.0.0.
